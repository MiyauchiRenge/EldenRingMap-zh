# 本分支的实现

本文说明代码组织、层契约、数据流与验证发布流程。游戏数据本身的字段与判定方法见
[机制.md](机制.md)；安装与使用见 [README.md](../README.md)。

本仓库为**交界地地图**（Lands Between Map），原为
[egormagurin/EldenRingMap](https://github.com/egormagurin/EldenRingMap) 的简体中文分支，
现已独立维护、不再跟踪上游，由 **MiyauchiRenge** 维护。程序仅读取本机游戏文件与存档，
不修改其中任何内容。

---

## 1. 目录与模块边界

```
Setup.bat / Start Map.bat / Start Map.vbs     安装与启动（Windows）
tools/
  erlib/            库：归档读取、参数表、消息表、MSB、DCX/KRAK、EMEVD、ESD、层契约
  extract_*.py      每层一个抽取器，只读游戏，只写 data/<层>.json
  build_markers.py  赐福、地标、Boss、地图碎片、地区名
  fetch_docs.py     安装时获取社区格式文档（仅此一步访问网络）
  dev/              复核脚本与后处理（不属于安装流程主体，见第 7 节）
server/
  index.js          路由、存档监视、SSE、角色切换、退出看门狗
  lib/              saveParser / slotWalk / project / bnd4 / respond
web/
  index.html        页面骨架与中英标题
  js/i18n.js        zh / en 两套键与语言切换
  js/map.js         画布、瓦片、缩放、投影
  js/               catalog / core / region（ES 模块）与入口 app.js
data/               生成物（仅 README.md 进仓库）
docs/               机制.md（游戏数据）与本文（实现）
```

约束：

* `tools/erlib/` 只提供读取游戏数据的能力，不含业务判断；
* 抽取器之间不互相调用，仅共用 `build_markers.place()` 的坐标投影；
* 服务端与客户端不包含任何具体层名，层名仅出现在注册表中（第 2 节）。

用词约定：本文称注册表中的每一项生成文件为**数据层**（data layer，如 `markers`、`gather-nodes`），
称地表、地底、幽影地为**地图层**（map layer，`M00` / `M10` / `M30` 等）；界面上的「图层」面板指
地图层，`/api/layer/<id>` 指数据层。

## 2. 层契约与注册表（`tools/erlib/layers.py`）

每份生成文件（数据层）在单一注册表中声明：文件名、生成工具与其参数、是否必需、进度口径
（`counts` / `spots`）以及下发方式（`initial` / `lazy`）。该模块同时提供唯一的写出函数与自检命令。

| 入口 | 作用 |
|---|---|
| `write_layer(id, markers)` / `write_doc(path, markers)` / `write_raw(path, doc)` | 统一写出：`{"locales": ["en","zh"], "markers": [...]}`、键排序、紧凑分隔符、LF 换行、临时文件加 `os.replace`（避免读到写入中的文件） |
| `python tools/erlib/layers.py check` | 输出每层标记数，并核对 `Setup.bat` 与注册表是否一致（漏跑、多跑、参数缺失均会报告） |
| `python tools/erlib/layers.py policy` | 生成 `data/layers.json`（分类所属层与进度口径，供客户端使用） |

实测结果：同一工具连续两次运行的输出逐字节相同；全部数据层体积 9.53 MB → 8.54 MB（紧凑分隔符）。
该自检已发现 `Setup.bat` 漏跑 4 个数据层（EMEVD 奖励、任务与事件奖励、商店货架、数量标注），现已补齐。

有坐标的标记合计 **28,177 个**。新增数据层只需在注册表中增加一行、运行抽取器并重新生成策略文件。

**进度口径**：`spots` 表示"该处可以找到某物"而非"某物仅可获得一次"（可刷新的采集点与敌人掉落），
计入完成度会导致进度无法达到 100%。两条细化规则写入 `data/layers.json`：一次性节点
（`once: true`）仍计入；**同时出现在点位层与计数层的分类按计数层计**——本机有 35 个此类分类
（`smithing_stone_*`、`glovewort_*`、`somber_stone_*`）。注册表判定与客户端原规则在 202 个分类上
无差异（`layers.py check` 每次核对）。

## 4. 服务端

`server/index.js` 负责路由、按 `--poll` 间隔监视存档并推送快照（SSE）、角色切换与记忆、页面关闭后
自动退出（`--idle-exit`，默认 150 秒；`--no-idle-exit` 关闭该行为）以及只读存档解析。

`server/lib/`：

* `saveParser.js` / `slotWalk.js`：读取存档中的角色、旗标与位置；
* `project.js`：与 `tools/build_markers.py` 一致的坐标投影，保证服务端与标记使用同一坐标系；
* `bnd4.js`：读取归档索引；
* `respond.js`：响应层。JSON 与文本按 `Accept-Encoding` 选择 brotli 或 gzip，编码结果按内容 ETag
  缓存（文档在启动后不再变化，逐请求重新压缩的开销高于发送）；条件请求返回 304；
  `/tiles/**` 与 `/icons/**` 走文件流并设置一天缓存；静态文件的目录逃逸检查也在此处
  （使用 `path.relative` 判断，而非字符串前缀）。

**接口**：`/api/markers`（首屏标记文档、地区表、层策略）、`/api/layer/<id>`（懒加载层）、
`/api/state`、`/api/saves`（GET/POST，切换存档与角色）、`/api/events`（SSE）、`/api/check`（勾选）、
`/api/refresh`、`/api/ping`、`/api/bye`（校验 Origin 为本机）、`/api/shutdown`。

**首屏下发**：`followup` 与 `gather-nodes` 在注册表中标记为 `lazy`，首屏不下发，页面首帧后并行请求并
合并；请求失败仅缺少对应标记。实测首屏标记文档 8,564,838 B → 1,560,023 B（未压缩）→ 173,122 B
（brotli，−98%），首屏标记数 28,156 → 5,970；懒加载的采集点为 385,863 B、后续物品为 55,417 B。

## 5. 客户端

客户端由五个文件、两类加载方式组成，不使用打包器：

| 文件 | 角色 |
|---|---|
| `web/js/i18n.js` | 传统脚本，定义 `window.I18n`（`zh` / `en` 同键、语言切换、名称拼接） |
| `web/js/map.js` | 传统脚本，定义 `window.TileMap`（画布、瓦片、缩放、投影） |
| `web/js/catalog.js` | ES 模块，纯数据表：分类行（含按等级派生项）、分组与顺序、颜色与半径、图例覆盖 `CAT_ICON`、渲染常量 |
| `web/js/core.js` | ES 模块：`state`、`$`/`t`/`nameOf` 等助手、图标加载、`isFound`、进度口径（`applyLayerPolicy` 供 `isNoProgress` 使用）；地图实例亦在此，由 app.js 通过 `setMap()` 注入 |
| `web/js/region.js` | ES 模块：地区标签、最近地名、`placeLabel`（"地区（最近地名）"一行） |
| `web/js/app.js` | ES 模块入口：交互与渲染（拾取、卡片、侧栏、进度、存档联动、SSE、懒加载合并），`boot()` 在此调用 |

依赖方向单向：`app → {core, region, catalog}`、`region → core`、`core → catalog`，无循环依赖。
拆分仅移动声明并保留原有名称，app.js 的函数体未作修改。

验证方式（无需浏览器）：`_test_client_modules.mjs` 在 Node 中以轻量 DOM 桩加载完整模块图，执行
`boot()` 至其开始等待服务器，并对抽出的模块做行为断言（`escapeHtml`、进度口径、`sharedRun`、
`placeLabel`、`regionFor`、分组表完整性）。该测试曾发现 app.js 缺少 `$` 导入
（`ReferenceError`），而静态检查未能覆盖。`_bench_client_draw.mjs` 以真实数据驱动实际绘制回调
（TileMap 桩捕获 `drawOverlay`），测量结果：

| 场景 | `drawMarkers()` 单次耗时 |
|---|---|
| 全部数据层（28,177 个标记，201 个分类开启） | 5.09 ms |
| 首屏（不含 22,206 个懒加载标记，5,971 个） | **1.93 ms（38%）** |
| 全部数据层，切到 `M10` 地图层 | 1.91 ms |

测量环境为 Node 与模拟 canvas，不进行实际栅格化，故为下限值；其意义在于懒加载将首屏绘制开销
降至约 38%。

其他实现要点：

* 分类与图例按 `data/layers.json` 建立（首屏数据含 121 个分类，策略文件声明 202 个），
  懒加载层的分类不会在数据到达前被剔除，已保存的勾选状态亦不受影响；
* 玩家标记取存档记录的最后位置（本分支已移除读取游戏内存的实时模式）；
* 同点位列表、Boss 聚合豁免与"此处还有"的固定顺序见 [机制.md](机制.md) 第 9 节。

## 6. 安装与启动脚本

`Setup.bat`（17 步，全部数据在本机生成）：

1. 安装 Python 依赖 → 2. 获取社区格式文档（paramdefs、旗标表、MFG id 列表；取来的文件不进仓库）→
3. 抽取瓦片 → 4. 生成标记 → 5. 索引地图文件 → 6. 抽取道具、商人与角色掉落 → 7. 抽取图标 →
8–15. 依次运行各数据层抽取器（EMEVD 掉落、EMEVD 奖励、刷取点、后续物品、采集点、任务奖励、商店货架、
数量标注）→ 16–17. 铃珠后处理（位置归到主人、商人标记写入 `dropsBell`）→
最后运行一次 `layers.py check`。

步骤编号不写死（早期使用 `[n/11]`，每次增层都需修改），注册表核对可保证不再漏跑数据层。

`Start Map.bat`：单一启动路径，启动服务并打开浏览器；参数原样透传（如 `--lan`）。
`Start Map.vbs`：隐藏窗口启动，日志写入 `logs\map-server.log`，并将 `pause` 的输入接到 NUL，
避免隐藏窗口中的错误分支阻塞。`tools/probe-python.bat`：通过实际执行判断 Python 可用性，
规避 Windows 上 `python.exe` 为微软商店占位程序的情况（`where python` 可找到但不执行任何操作）。

## 7. 验证与发布流程

每次改动按以下顺序执行：

1. **重跑**：涉及数据的改动重跑受影响的抽取器或整条流水线，输出每步真实退出码与结果；
2. **自查**：`layers.py check`（层与 Setup 一致性、进度口径等价性）、逐文件语法检查
   （Python `compile()` 与全部 `.js` 的 `node --check`）、必要时在本机端口启动服务做冒烟测试；
3. **更新记录**：写入 [README](../README.md) 的「六、更新记录」；
4. **压缩为单条提交并强推**；
5. **逐字节核对**：对每个跟踪文件比对 `git show HEAD:<path>` 与工作区字节，并核对远端 SHA。

`tools/dev/` 包含两类工具：

* **复核脚本**（可重复运行）：`gather_lifetime_check.py` 以存档复核采集点寿命位、
  `verify_with_save.py` 以存档复核已拾取状态、`shop_register.py` 复核货架归属、
  `place_from_save.py` 以角色当前坐标落点；
* **后处理**（`Setup.bat` 第 16、17 步，在全部数据层生成后运行）：`fix_bell_positions.py` 按 `NpcParam`
  的 lot 将商人铃珠移至主人坐标（`via: bell-owner`），`link_bell_bearings.py` 为商人标记补充
  `dropsBell` / `dropsBellPx`。

一次性调查脚本在使用完毕后删除，其结论记录于 [机制.md](机制.md)，可重复运行的检查保留在上述工具中。
商人命名曾存在两个实现（`extract_items.py` 的"种类（最近赐福）"与已删除的 `rename_merchants.py`
的旧式"种类·地点"），后者未出现在任何发布数据中，已随清理删除。
