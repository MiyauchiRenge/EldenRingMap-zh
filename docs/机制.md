# 游戏数据机制

本文记录游戏数据的读取方式：字段位置、判定规则与验证结果，供后续维护与复核使用。
代码结构与流程见 [实现.md](实现.md)，安装与使用见 [README.md](../README.md)。

文中所有数字均在本机游戏文件与真实存档上实测得到；判定类结论均附复核方式。

---

## 1. 标记名：取自游戏官方中文文本

标记名与派生名均来自游戏自带的消息表：`/msg/zhocn/item.msgbnd.dcx` 与
`item_dlc02.msgbnd.dcx`（`tools/build_markers.py` 的 `LOCALES = {"en": "engus", "zh": "zhocn"}`）。
中文名与英文名使用同一键、同一张表，派生名（例如"某地·流浪民族的商人"）由游戏地名拼接，
不存在人工翻译表。界面文案单独维护于 `web/js/i18n.js`（`zh` / `en` 两套键，见 [实现.md](实现.md)）。

## 2. 物品图标：`EquipParam*` 五张表的图标字段

道具标记显示物品自身图标，编号取自 `regulation.bin` 的五张参数表
（`tools/extract_items.py` 的 `ICON_OFFSETS`）：

| 参数表 | 字段 | 宽度 | 物品类别 |
|---|---|---|---|
| `EquipParamGoods` | `+0x030` | s32 | 道具：铃珠、卢恩、锻造石、种子、露滴、骨灰、消耗品等 |
| `EquipParamWeapon` | `+0x0BE` | u16 | 武器与弹药 |
| `EquipParamProtector` | `+0x0A8` | u16 | 防具 |
| `EquipParamAccessory` | `+0x026` | u16 | 护符 |
| `EquipParamGem` | `+0x004` | u16 | 战灰 |

后四个字段宽度为 2 字节。若按 4 字节读取，相邻字段的值会并入高位，导致相邻行非零的物品显示为
其他物品的图标（例如防具行显示护符图标）。当前读法已与外部对照表逐条比对：护甲 50/50、武器
133/133、弹药 69/69、护符 73/73 一致；其余差异全部为对照表未覆盖的 DLC 新增行。

防具字段 `+0x0A8` 的语义：按 Paramdex 定义，`EquipParamProtector` 的 `iconIdM` 位于 `0xA6`、
`iconIdF` 位于 `0xA8`，即当前读取的是女性图标。全表 838 行中仅 12 行 `iconIdM != iconIdF`，
且这 12 行均非地图拾取点（已反查 63 个防具标记，受影响 0 个），该选择对数据无影响。

图标按需抽取：仅地图实际使用的 `iconId`（以及图例指定项）会写为 PNG。当前包含
**89 个地图与分类图标**（`web/icons/*.png`）与 **875 个物品图标**（`web/icons/items/*.png`，
22.8 MB）。图标素材不进仓库（见 `.gitignore`）。

## 3. 图例图标：`CAT_ICON` / `LEGEND_ICON_IDS` / `EXTRA_ITEM_ICONS`

分类行默认使用该分类下物品自身的图标（锻造石与黄金卢恩按等级可直接区分），无图标时退回
彩色圆点；上游随附的第三方分类图标因此不再分发。推断结果不适用的分类由 `web/js/app.js` 的
`CAT_ICON` 显式指定：

| 分类 | 指定图标 | 说明 |
|---|---|---|
| 角色掉落·武器 | 暗月大剑 10089 | |
| 角色掉落·防具 | 雪魔女尖帽 14740 | 游戏正式名为"雪魔女尖帽" |
| 角色掉落·护符 | 观星少女的传说 18090 | |
| Boss 掉落 | 追忆 163 | |

上述图标没有被任何标记引用（仅供图例行），因此列入 `tools/extract_icons.py` 的
`LEGEND_ICON_IDS` 一并抽取；"分类显示指定物品图标"的覆盖项列入 `EXTRA_ITEM_ICONS`。
当前缺失图标数为 0。

## 4. 按等级拆分的分类：锻造石、铃兰、卢恩

- **锻造石**：游戏 id 将两个类别交错排列，按掉率分组无法表达"锻造石【3】"。现按
  `SMITHING_LEVELS`（id → 等级与是否失色）拆分为 `smithing_stone_1`…`_8`、`somber_stone_1`…`_9`，
  另有 DLC 的 `smithing_stone_shadow` / `_legend` 与 `somber_stone_shadow` / `_legend`。
- **铃兰**：原实现将 49 个标记置于同一分类（墓地铃兰【1】【5】–【9】与灵依墓地铃兰【5】–【9】混合），
  图例图标只能取其中一个等级。现按类别与等级拆分（`glovewort_grave_1`…、`glovewort_ghost_1`…），
  另设两行无等级的"大朵"。地图上有放置点的 13 行会显示；其余 7 个等级仅存在于敌人的可刷掉落
  （`ItemLotParam_enemy`）与商店表中，地图本身没有放置点。
- **卢恩**：按 `RUNE_LADDER` 分为类别与等级（黄金 13 级、英雄 5 级、幽影 7 级），等级取自游戏物品名
  （如"黄金卢恩【7】"），不另行编号。
- 标签按游戏译名修正：`whetblades` 砥石小刀 → 砥石刀、`lost_ashes` 丢失的战灰 → 失力战灰、
  `prattling_pates` 多话的帕特 → 唤声泥颅。判定方法是将 101 个分类（含商人共 102 个）的标签与其
  实际包含的道具名做全量比对。

## 5. 地区名：`WorldMapPlaceNameParam` 与最近矩形判定

界面原先只显示地图层名称（`M00` → "交界地"，`M10` → "幽影之地"），对定位没有帮助。现使用游戏
自身的地区标签：

- **数据来源**：`WorldMapPlaceNameParam` 每行给出所属地图碎片（`worldMapPieceId`，碎片的
  `openTravelArea` 已是主图像素）与地区分组（`areaNo`：10/60 地面、12 地下、61 DLC）。
- **产出**：`tools/build_markers.py` 的 `build_regions()` 写出 `data/regions.json`。
- **判定**（`web/js/app.js`）：取距离最近的地区矩形（矩形内距离为 0，超过 400 主图像素不计入）；
  无邻近矩形时回落到 `default`，即开局赠送、没有地图碎片的宁姆格福。由于矩形范围窄于地区本身，
  另加一条规则：最近地名的名称若包含地区名（"利耶尼亚湖（湖边）"与"湖之利耶尼亚"共享"利耶尼亚"），
  以名称判定为准。
- **交叉验证**：判定结果与社区商人清单一致（"East Altus Plateau - Hermit Merchant's Shack" →
  亚坛高原；"North Caelid (Dragonbarrow) - Isolated Merchant's Shack" → 盖利德）。

## 6. 采集点寿命位（一次性 / 可刷新）

`AssetEnvironmentGeometryParam` 的同一行同时描述"该节点给予什么"与"是否再生"：

* `+0xB8`：`pickUpItemLotParamId`，指向该节点的 lot；
* `+0x3C` 的字节为寿命位：`0x60`（第 5、6 位同置）表示采集后不再生，`0x40` 表示休息后再生，
  `0x00` 的 16 行在世界上没有对应节点。

判定方法（不使用任何第三方数据）：将带拾取 lot 的 321 行逐字节、逐位与存档的 `WorldGeomMan2`
（魔数 `FOEG`）比对。该区块仅记录永久拾取的节点，其列出的行必然为一次性。结果：该区块列出的
44 行全部为 `0x60`；其余 277 行中 260 行为 `0x40`，剩余 17 行为从未采集的稀有材料
（锻造石【６】【７】、失色锻造石【２】–【８】、大朵墓地铃兰、亚缇莉亚叶与四种 DLC 材料）。
同一判定在第二份存档（1,669 旗标）上结果一致。复核脚本：
`tools/dev/gather_lifetime_check.py`。

接线：`tools/extract_gather_nodes.py` 为每个采集点写出 `once` 字段；客户端将 `once` 节点计入收集进度，
可刷新节点按"处"统计（口径见 [实现.md](实现.md) 第 3 节）。

## 7. lot 编号规律与奖励发放方式判定

`ItemLotParam_map` 的编号格式为 `<lead><area:2><grid:2><seq:4>`：

| `lead` | 含义 |
|---|---|
| 10 | 本体地表（`m60_XX_YY_ZZ`） |
| 20 | 幽影地（`m61_XX_YY_ZZ`） |
| 30 | 地下 |
| 60 | 少数九位数编号 |

该规律以已落点的 6,958 个 lot 验证：命中 1,669 个。旧读法（`lot // 10_000_000`）命中 18 个，
是旧版任务奖励层无法落点的原因。

任务与事件奖励层（`data/quest-rewards*.json`）的收录条件为：lot 的 `getItemFlagId` 已在存档中设置，
且没有任何世界物件引用该 lot（不是宝箱、采集点、已放置角色或刷取点）。
`tools/extract_quest_rewards.py` 按下表顺序取证据，命中即停，并将证据写入条目的 `note`：

| 判定 | 依据 | 本机条数 |
|---|---|---|
| `event-instruction` | EMEVD 指令的操作数等于该 lot；仅采信 6 位以上的 lot（lot 2000 在 543 个事件文件中命中 9,929 次常量） | 0 |
| `event-record` | EMEVD 参数段存在 `(type, entity, entityFlag, lot)` 记录且 `entity == entityFlag > 1000`；该形状在已知由事件发放的 lot 上验证为 199/199 | 1 |
| `event-flag` | EMEVD 指令包含该物品的旗标 | 0 |
| `shop` | `ShopLineupParam` 存在出售该物品的行，且 `equipType` 与物品类别一致（编号体系：0 武器／1 防具／2 护符／3 道具／4 战灰；不做该检查会产生 17 条误判） | 71 |
| `lot-map` | 符合上述 lot 编号规律 | 20 |
| `starting` | 旗标位于 60000–60999，由游戏在角色创建时设置 | 7 |
| `unreferenced` | 以上均不命中，记录旗标段与该段内已落点标记的构成 | 333 |

位置取自：前三类取该实体自身的已放置标记，否则取该事件所在地图的 Boss 标记，否则取该地图首个赐福；
`shop` 取货架所属商人；`lot-map` 取对应地图的 Boss 或赐福；`starting` 与 `unreferenced` 不生成坐标。
结果：**26 条有坐标，420 条仅登记判定与理由**。

`unreferenced` 类为负结论：`getItemFlagId` 在物品获得时自动设置，因此可确认该物品已被获得、
以及其所属旗标段（本机集中在 400xxx 196 条、520xxx 51 条、510xxx 37 条），但游戏数据中没有任何
脚本或物件指向发放者。进一步定位需要"对话脚本设置任务旗标 → EMEVD 依据该旗标发放"的链路，尚未实现。

## 8. 商店货架：由 talk ESD 声明的行段

`ShopLineupParam` 包含物品、价格、数量与库存旗标，但不含商人信息；`NpcParam` 也没有货架字段。
实际结构为：一个货架是 `ShopLineupParam` 中一段连续行，由说话脚本（talk ESD）声明，两种形式：

* `bank 1 cmd 22`，参数 `(first, last)`；
* `bank 6 cmd 2147483610`，参数 `(flagA, first, last, flagB)`，两个旗标由地图号拼接
  （例如 `m60_43_53` → `1043530701` / `1043532700`）。

脚本与地图部件的对应关系：部件实体数据 `+0x50` 为 talk id，脚本文件为 `t<talkid>.esd`
（`tools/erlib/esd.py` 为自研 ESD 读取器，358 个脚本全部通过结构自检）。
`tools/dev/shop_register.py` 据此将货架归属到具体商人：8 行货架中 **6 行落到具名商人**，
其中 5 行为流浪／遁世等商人自述的行段，1 行为幽影之地的休里耶；其余 2 行（`600014`、`1600115`）
没有任何脚本声明，按"无归属"记录。

商人数量的判定：`c3200`（流浪民族商人）部件共 29 个，其中 8 个指向没有驮马的占位行；
其余 21 个标记对应 **20 个商人**——商人 `32001520` 在原版数据中有两处放置（远眺岛与利耶尼亚湖湖边，
各带一头驮马），货架段数 20 与商人数一致。

**为什么其余的商店行无法归属（调查结论，避免重做）**：`ShopLineupParam` 共 **1,296 行**，18 个字段里
没有任何"店铺/商人"字段，`NpcParam` 也没有；194 张参数表里不存在"店铺 → 行段"的链接表
（另有 `ShopLineupParam_Recipe` 188 行，属制作台，无 paramdef）。可读的 358 个 talk 脚本只声明了
**8 段**行段（全是制作台类商店：龟裂壶／调香瓶），覆盖 147 行；按 `eventFlag_forStock` 分组得到
785 组（其中 747 组只有 1 行），说明库存旗标是**按物品**而非按店铺的，无法据此还原货架。归档索引
只存路径哈希、没有路径名，因此**无法枚举**菜单类 ESD；按候选路径探测（`/script/menu/…`、
`/script/shop/…` 等 6 个）全部不存在。结构性线索只有一条：已登记的 6 个普通货架都落在**对齐到 25 的
连续行块**内（`100500`、`100525`、`100600`、`100725`、`100825`、`102270`），据此可枚举出约 52 个货架块，
但**块本身不含归属**，没有归属就没有坐标，落不了点。因此本分支的商店层维持"能归属的才登记"：
8 个货架 + 2 个无归属（`600014`、`1600115`）。若要继续补，只能为此建一张**人工核定表**
（每块一行，标明归属商人），不适合自动流程。

## 9. 同点位多标记的成因与处理

按"同一地图层且像素距离 ≤ 3"做连通分组，28,180 个有坐标标记中共有 **2,651 组重叠，涉及 8,028 个标记**；
其中 **886 组为完全同坐标**（3,212 个标记），112 组包含 Boss。成因三类：新增掉落叠加在给予者身上
（Boss 掉落与一次性奖励）、同名采集物聚集（单处最多 12 个拉答果实，各有独立旗标）、以及上游已有的
一地多标。

客户端 `pick()` 原先只返回最近标记，被覆盖的标记无法选中。现按屏幕距离收集一组（阈值 6 屏幕像素），
卡片中增加"此处还有"列表，逐条可点、顺序固定、当前项以方框标示。`cluster()` 则将 Boss 排除在气泡
聚合之外并绘制在气泡之上。

## 10. Boss 掉落的人工核定表

部分 Boss 击杀奖励由 EMEVD 直接按 lot 发放，自动流程（邻域与名称匹配）无法确定归属。为此保留人工
核定表 `data/boss-drop-overrides.json`（不进仓库）：条目仅补充"归属哪个 Boss"，lot、旗标与物品名仍全部
来自游戏数据；标记落在对应 Boss 坐标，`via: curated`。

当前状态：本机不存在该文件，故 curated 记录为 0 条，`boss-drops.json` 的 152 条全部来自脚本判定
（`via` 仅有 `name` 与 `script`）。

## 11. 存档读取范围（只读）

服务端仅读取本机存档，从不写入：

* **事件旗标**：按 `data/eventflag_bst.txt`（旗标分块表）逐块读取，用于判断标记的获得状态。
  已在 7,447 旗标与 1,669 旗标两份存档上验证。
* **角色与位置**：每个角色的最后存档位置（主图像素）、等级与游戏时长，用于玩家标记与角色切换。
* **`WorldGeomMan2` 两个区块**：`MOEG`（已破坏或已拾取物件）与 `FOEG`（永久拾取的一次性节点）。
  记录长度 8 字节：`key = instance << 15 | state`、`model = 10000000 + AEG id`，按地图分段。
  本项目仅用于第 6 节的寿命位复核，不作为已拾取状态的唯一来源。
