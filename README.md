# 交界地地图

[English](README.en.md) · [游戏机制](docs/机制.md) · [实现与流程](docs/实现.md)

艾尔登法环（Elden Ring）的本地交互式地图，中文优先，由 **MiyauchiRenge** 维护。
标记、分类与进度全部由本机游戏文件与存档生成：程序只读，不修改游戏，也不修改存档。
引擎来源与许可说明见文末「五、来源、授权与免责声明」。

---

## 一、功能

* **交互式大地图**：地表、地底、幽影地各层，支持缩放、平移与地图层切换；
* **标记与分类**：赐福、地标、Boss、地图碎片、道具、采集点、可刷点、商人、角色掉落、Boss 掉落、
  事件给予、商店货架、任务与事件奖励等；每个分类一行，可勾选并统计进度，行图标使用物品自身图标；
* **进度口径**：区分一次性获取与可重复获取。可刷新的采集点按"处"显示且不计入完成度，一次性节点
  计入；规则由数据下发（见 [docs/实现.md](docs/实现.md) 第 3 节）；
* **同点位多标记**：同一位置的多个标记可逐条选择（卡片内"此处还有"列表），Boss 不参与气泡聚合；
* **地区与最近地名**：标记与玩家位置均显示游戏自身的地区名与最近地名；
* **存档联动**：读取存档中的已拾取状态与角色最后位置，用于勾选、进度与玩家标记（只读）；
* **两种启动方式**：`Start Map.bat`（可见控制台）与 `Start Map.vbs`（隐藏窗口）；页面关闭后服务自行退出；
* 简体中文界面，名称取自游戏官方中文文本。

## 三、实现要点

* **采集点**：地图资产部件名形如 `AEG{xxx}_{yyy}_{instance}`，其中 `AEGxxx_yyy = xxx*1000+yyy` 为
  `AssetEnvironmentGeometryParam` 的行号；该行 `+0xB8` 指向 `ItemLotParam` 的 lot，`+0x3C` 为寿命位
  （`0x60` 一次性 / `0x40` 可刷新）。扫描 1,248 张地图的 621,538 个部件后得到 19,263 个采集点，
  其中一次性 1,661 个，并以存档的 `FOEG` 区块（仅记录永久拾取）逐条复核。
* **存档世界状态**：存档槽在事件旗标之后含两个区块：`MOEG`（已破坏或已拾取物件）与 `FOEG`
  （永久拾取的一次性节点）。记录长度 8 字节：`key = instance << 15 | state`、
  `model = 10000000 + AEG id`，按地图分段。
* **任务与事件奖励**：446 条"旗标已设置但没有任何世界物件引用"的 lot，逐条取证判定（事件指令、事件记录、
  商店货架、lot 地图位、开局段、无引用），其中 26 条落到坐标，420 条仅登记判定与理由。
* **验收结果**：`FOEG` 已拾取节点 321/321 均可在地图上找到；存档旗标漏点 0；采集物图标 114/114 完整；
  坐标核对误差 0.2 像素。幽影树碎片 46 个点位 / 50 个物品，灵灰 23 个点位 / 25 个物品
  （部分点位一次给出两个）。

字段位置、判定方法与验证数字见 [docs/机制.md](docs/机制.md)；已知限制见文末「五、来源、授权与免责声明」。

## 四、安装

```
1. 运行 Setup.bat（数据全部在本机生成，17 步）
2. 运行 Start Map.bat（可见控制台）或 Start Map.vbs（隐藏窗口）
3. 在浏览器打开提示的地址
```

仅支持 Windows，需要 Node.js 18+ 与 Python 3（Python 仅用于安装阶段）。服务默认仅监听本机，
`--lan` 可开放到局域网。详细步骤与故障排查见 [docs/实现.md](docs/实现.md) 第 6 节。

### 传输与性能

* **抽瓦片：并行编码 + 增量重建**：实测一次 Setup 里 `extract_tiles.py` 耗时 **286.7 秒**，其中
  **266 秒（93%）在金字塔写盘**（每级 resize、分块裁剪、每张 WebP 编码），拼接只占 15 秒——与
  原先"瓶颈在解码"的猜测相反，因此只对写盘做并行、拼接保持串行。改为：每级的瓦片编码交给线程池
  （Pillow 写 WebP 时会释放 GIL，`--jobs` 默认 `min(6, CPU 核数)`），并把"这段源数据与参数已经建过"
  记入 `cache/tiles-state.json`，命中即整块跳过（`--force` 可强制重建）；中断后重跑时已存在的瓦片直接
  复用（因为参数未变则内容必然相同），manifest 由磁盘扫描重建。实测：**286.7 → 175.1 秒**
  （4 核机器的 4 线程，写盘 266 → 156 秒），**参数与源未变时 1.9 秒**（7,140 张全部复用）；
  两种模式下产物都与改动前**逐字节相同**（7,141 个文件、整树哈希一致、`manifest.json` 一致）。
* **响应层与压缩**：新增 `server/lib/respond.js`，JSON 与文本按 `Accept-Encoding` 选择 brotli 或 gzip，
  编码结果按内容 ETag 缓存；带 ETag，条件请求返回 304；`/tiles/**` 与 `/icons/**` 缓存一天，
  其余为 `no-cache`。实测：首屏标记文档 8,564,838 B → 1,560,023 B（未压缩）→ 173,122 B
  （brotli，−98%）；`js/app.js` 93,960 → 30,282 B、`js/i18n.js` 30,786 → 8,293 B、
  `css/app.css` 17,659 → 4,742 B；重复请求命中 ETag，返回 304 与 0 字节。
* **重层懒加载**：注册表新增 `client` 字段（`initial` / `lazy`），`followup`（855 KB）与
  `gather-nodes`（6.15 MB）标记为 `lazy`，服务端提供 `/api/layer/<id>`，页面首帧后并行获取并合并，
  失败时仅缺少对应标记。首屏标记数 28,156 → 5,970；懒加载层压缩后分别为 385,863 B 与 55,417 B。
  首屏数据含 126 个分类而策略文件声明 207 个，侧栏与勾选状态按策略文件建立，采集点分类不会因数据
  延迟到达而被剔除。
* **数据在启动时读入（需要重启服务才会生效）**：`data/*.json`（含 `layers.json` 层策略）只在服务
  启动时加载一次，而 `web/**` 的页面与脚本是逐请求读盘。这里踩过一次坑：重新生成 `layers.json`
  （新增每个分类的本地化名）后没有重启服务，客户端拿到的仍是旧策略，采集分类行只能回退到 i18n 里的
  英文材料名，于是中文界面的采集物分组里出现英文（中文侧栏也因此显得不对）。现已重启，
  并把"服务下发的策略必须与磁盘逐字节一致"加入服务冒烟自查，不一致即报错；
  [docs/实现.md](docs/实现.md) 第 4 节写明了这条约束。
* **渲染开销**：以真实数据驱动实际绘制回调测量，全部数据层（28,180 个标记、206 个分类）为 3.7–5.1 ms/次，
  首屏（5,974 个标记）为 1.2–1.9 ms/次，即懒加载将首屏绘制开销降至约 32–38%（Node 与模拟 canvas，
  未进行实际栅格化，为下限值）。
