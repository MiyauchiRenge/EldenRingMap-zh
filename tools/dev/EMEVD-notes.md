# EMEVD 掉落链：已证实的事实（链已解决，见文末）

本文是我们自己做 EMEVD 解析时的实测记录（全是**从游戏文件里量出来的**事实；参考项目
`EldenRingTool-main`（LGPL）**只用作验证基准**，其代码与数据都没有进入本项目）。

## 一、已经证实、可复用

### 1. MSB 部件里的实体 id（用于取坐标）
```
entity_rel = i64(part + 0x60)          # 指向实体数据
entity     = u32(part + entity_rel + 0x00)
npc        = i32(part + i64(part + 0x68) + 0x0C)   # 走类型数据，比扁平 0x2AC 更正规
位置        = vec3(part + 0x20) → LegacyConv 投影
```
验证：`m60_35_41_00` / `m60_37_42_00` 三个已知用例读出的实体 id 与参考项目记录**完全一致**
（`1035410340` / `1035410350` / `1037420200`）。

补充观察：**实体 id 与它的旗标相差 2000**（`1035410340` ↔ `1035412340`）。

### 2. EMEVD 文件头（int32 + 从 +16 起的 int64 段表）
```
+0   int32 magic "EVD\0" (0x00445645)
+8   int32 version = 205 (0xCD)
+12  int32 fileSize
+16  int64 eventCount
+24  int64 eventOffset      （实测恒为 144 = 0x90）
+32  int64 instructionCount
+40  int64 instructionOffset
+48  int64 ?                （0）
+56  int64 paramOffset
+64  int64 ?                （与 +56 相同）
```
**坑**：早期版本从 `+8` 按 int64 解析，导致每个字段错位一格、读出天文数字。务必从 **+16** 起。

### 3. 事件记录 = 48 字节 = 6 个 int64
```
[ id, instrCount, instrOffset, paramCount, paramOffset, ? ]
```
自检：`m60_35_41_00` 事件表 @144，4 条 ×48 = 192 字节 → 结束于 336，**正好等于头部的指令段偏移** ✓。
`paramCount` 为 `-1` 表示该事件没有参数。

### 4. 事件参数区（实体与旗标住在这里）
形状（`m60_35_41_00` 参数区 @1360 起）：
```
90005261 | 1035410340 | 1035412340 | 1.0 | 0 | 1700 | 0
   参数类型id     实体id      实体旗标      浮点参数…
```
**结论**：实体 id **不住在指令参数里** ✓ —— 指令参数里统计"实体出现率"的结果是 **0 个**
高比例位置（样本 6131 条指令、134 种 `(bank,id)`），已实测否决。

## 二、已实测否决的路线（不要再走）

| 路线 | 实测结果 |
|---|---|
| 字节窗口（±8…±128）找 lot 附近的实体 | 覆盖 64-65%，实体正确 90%，**天花板** |
| 跨文件全局同法 | 65% / 90%，与单文件无差别 |
| 指令参数里 lot 与实体共现 | 454 条里命中 4 条（1%）|
| 事件级共现 | 同上（1%）|
| 事件参数区"实体 + 旗标"配对 | 10/454（2%）|
| `[bank, id, argLen, pad] + args` 当指令记录 | 声明 95,727 条，只解析出 8,757 条（9%）✗ |

**正确结论**：ER 的指令参数长度**由 `bank/id` 决定**，不存在记录内的 argLen；把下一个
int32 当 argLen 会立刻走错（第 2、3 条指令处崩）。规范见：
- https://github.com/Nordgaren/SoulsFormats/blob/master/FORMATS.md （EMEVD 节）
- https://soulsmodding.com/doku.php?id=tutorial:intro-to-elden-ring-emevd （指令形如
  `DisplayBossHealthBar(Enabled, 18000850, 0, 904311000);`，参数带类型）

## 三、判定规则（已从参考项目的**逻辑**读出，尚未获得公平检验）
```
参数前 8 字节 = 槽位 + 被调用事件 id → 永远不是实体参数
从第 8 字节起、每 4 字节：第一个落在实体表里的值 = 实体
同一批参数里等于某 lot 的 getItemFlagId 的值 = 旗标 → lot
位置优先级：同图 > 同 10 字符区域前缀 > 其它（同优先级取 tier 最小）
```
**注意**：因为读取器还没对（见上表最后一行），前几轮用它打出的 1%/2%/0% **不能**用来
判断这条规则的对错。

## 四、验收标准（自证，不依赖参考项目）
1. 单文件解析出的指令数 **== 头部声明的 `instructionCount`**；
2. 全部 543 个事件文件的总解析数 **== 95,727**；
3. 通过后再用参考项目的 455 条 `unique_drops` 打分（目标：覆盖 ≥90%、实体正确 ≥90%）；
4. 达标才接进 `tools/extract_items.py`；不达标一律否决，绝不把未经证实的数据写进 `data/`。

## 五、当前缺口（用于判断"还差什么"）
- 参考项目 455 条基准中：297 个 lot 出现在事件文件里、209 个我方数据本来就有、
  **45 个既不在事件文件、我方也没有**（例：猎犬骑士铠甲/臂甲/腿甲 lot `429000801/02/03`、
  战灰类 lot `435110106`、武器 lot `435300706`）。这 45 条就是 EMEVD 链要补的目标。
- 铃兰阶梯还缺 3 行：`墓地铃兰【３】`、`灵依墓地铃兰【１】`、`灵依墓地铃兰【３】`。

## 六、结局（已解决）

参数区里的四元组 `[事件 id, 实体 id, 实体旗标, lot id]` 就是整条链：奖励 lot 直接与发放它
的地图实体对应，坐标取该实体在 MSB 里的位置。过滤器 `实体 == 旗标 且 事件 id > 1000` 在
455 条基准上实测 **189 条命中、实体 100% 正确**。

落地：`tools/extract_emevd_drops.py` → `data/emevd-drops.json`（本机 **272 条**标记，
无摆放跳过 54、无名称跳过 3）→ 由 `server/index.js` 合并 → 计入收集进度。

仍未解决：铃兰阶梯最后 3 行（`墓地铃兰【３】`、`灵依墓地铃兰【１】【３】`）—— 它们的载体
既不在事件脚本、也不满足 NpcParam 的 `itemLotId_enemy` 链（含已验证的兄弟 lot 规则），
属"游戏未给固定位置"（商店出售 / 随机敌人掉落）。
